# 《CodeSage项目》——支线三：工程实录（性能与测试）

> 📍 **主线进度**：主线（01–08）已完结；本篇是**支线三**。这一篇不讲功能，讲"这个工程是怎么做出来的"——一次 44 倍性能优化、一张测试地图、一份容错清单，以及一份"用户反馈驱动修复"的完整台账。

## 11.1 44 倍性能优化实录

这是项目最有叙事感的一段工程史——起点和终点都是真实测量。

**起点：一次尴尬的自举审查。** 用 CodeSage 审查自己的源码（62 个文件），全量审查耗时 **92.7 秒**。一个"AI 代码审查工具"看不了自己的代码，说不过去。

**定位：cProfile 逐层剖析。** 耗时分布出来后，三个大头浮出水面——全部在"进程模型"和"I/O 模型"层面，**没有一个涉及算法**：

| 阶段 | 优化前 | 优化后 | 手段 |
|---|---|---|---|
| Bandit 扫描 | 90s+ | ~8s → 1.5s | 逐文件子进程调用（每次 ~1.5s 启动成本）→ 单次批量扫描目录 |
| Ruff 扫描 | ~7s | ~0.2s | 同上 + 直接扫描真实目录（不再复制源码） |
| 临时目录写删 | ~7s | 0s | cProfile 显示 `nt.remove`/`nt.rmdir` 删除 62 个文件占 6.7s（Windows 文件系统挂钩开销）→ 改为零临时文件设计 |
| **总耗时** | **92.7s** | **2.1s** | **约 44 倍提速** |

### 修复一：Bandit 批量扫描

问题根源是**子进程启动成本**。`bandit_runner.py` 头注释：

```python
"""Bandit 集成：安全漏洞扫描（SQL 注入 / 命令注入 / 反序列化等）。
...
性能设计（批量模式）：
Bandit 每次调用要付出解释器启动 + 依赖导入的成本（约 1.5s），
逐文件调用在 60+ 文件的仓库上会耗时 90 秒以上。
run_batch 把所有源码写入临时目录（保持相对路径结构），
一次 `bandit -r` 完成扫描——这是自举审查（用 CodeSage 扫自己）发现的优化点。
"""
```

62 个文件 × 1.5 秒 ≈ 93 秒——**耗时几乎全是解释器启动，和代码本身毫无关系**。批量模式把 62 次调用合并成一次 `bandit -r <目录>`（递归扫一个目录，启动成本摊薄到趋近于零）。调用方在 pipeline 的批处理分支（第 03 篇 3.1）：

```python
        if getattr(analyzer, "supports_batch", False):
            batch = analyzer.run_batch(sources, base_dir=workspace)
```

### 修复二：零临时文件设计

第一版"批量"是把源码写进临时目录再扫——但 cProfile 发现了更隐蔽的成本。`ruff_runner.py` 的注释记录了实测结论：

```python
        """批量扫描。

        性能设计（cProfile 实测的优化结论）：
        - 临时目录模式在 Windows 下有隐藏成本：删除 62 个文件实测 6.7s
          （nt.remove/nt.rmdir，杀毒软件与文件系统挂钩导致）；
        - 因此提供 base_dir 参数：源码本来就在磁盘上时（pipeline 与 eval
          的全部真实场景），直接扫描真实目录——零临时文件、零清理成本。
        临时目录模式仅作兜底（调用方仅有内存源码时）。
        """
```

**删除 62 个临时文件要 6.7 秒**——在 Windows 上，每个文件的删除都要过杀毒软件与文件系统过滤驱动，`nt.remove` / `nt.rmdir` 的系统调用开销远超直觉。这个数字只有 cProfile 给得出来（盯着代码看一万遍也想不通"删文件为什么这么慢"）。解法是一次接口重审：**源码本来就在磁盘上**（审查真实项目时），为什么要复制出去再扫？于是 `run_batch` 增加 `base_dir` 参数——有真实目录就直扫真实目录；只有"调用方手里仅有内存源码"（如单文件调试）才回退临时目录。`bandit_runner.py` 同样跟进（两处实现对称）。

### 修复三：方法论

最值得学的不是任何一行代码，而是流程本身。README 的总结：

> 这次优化本身也是评测驱动开发的例证：先有量化基线（Harness 记录每次耗时），再做剖析，最后用数据验证收益。

三步都可以复述到面试里：**有基线**（92.7s 是被记录下来的数字，不是感觉）→ **有剖析**（不猜，cProfile 说话）→ **有验证**（改完 2.1s，同样是测出来的）。还有一个容易忽略的起点：**这些优化是"自举审查"（dogfooding）暴露的**——用自己审查自己，才会真在乎"审 62 个文件要一分半钟"这件事。

## 11.2 测试体系：14 个文件、119 个用例

全量跑完 **4.4 秒**（`119 passed`）。每个文件守一类事实，分布与"守什么"：

| 测试文件 | 用例数 | 守什么 |

| `test_cli_helpers.py` | 9 | CLI 辅助逻辑（`-o` 目录感知、`--project` 归一化） |
| `test_metrics.py` | 8 | 软匹配器（行区间 + 关键词）与聚合 |
| `test_ingest.py` | 7 | 扫描过滤 / 大文件跳过 / gitignore / 切块 / diff 区间 |
| `test_noise_control.py` | 7 | 误报控制回归（208 条事故档案） |
| `test_severity_mapping.py` | 7 | 高危规则严重级上调（安全与质量的可比性） |
| `test_memory.py` | 6 | 三区组装 / 压缩触发 / 压缩失败保护 |
| `test_models.py` | 6 | 去重策略（跨来源合并 / 同来源保留 / 优先级） |
| `test_registry.py` | 6 | schema 生成 / 执行容错 / 参数过滤 |
| `test_store.py` | 6 | 全局存储的项目隔离与旧库迁移 |
| `test_tools.py` | 6 | submit_finding 换行归一化与去重 |
| `test_tokenizer.py` | 6 | 估算器（CJK / ASCII / 消息开销，区间断言） |
| `test_changed_mode.py` | 4 | `--changed` 三态语义（需 git，无 git 自动跳过） |

三类最值得引用的测试设计。

**其一：正反例成对**（`test_ast_rules.py` 头注释）：

```python
"""AST 规则引擎测试：每条规则 正例 + 反例 成对出现。

为什么正反例成对：规则的"漏报"与"误报"是两个独立缺陷，
只用正例测不出误报（over-triggering）。
"""
```

实践形态：`test_cg001_mutable_default_positive` 断言 `def f(x=[])` 被抓到；`test_cg001_mutable_default_negative` 断言正确写法（`x=None` + 函数内创建）**不**被误抓——13 条规则全部这个格式，30 个用例大部分是这种成对结构。

**其二：Mock 驱动的循环测试**（`test_agent_loop.py` 头注释）：

```python
"""Agent 循环测试：Mock 客户端驱动，不依赖网络与 API Key。

覆盖（对应规划文档的循环设计要点）：
- 工具调用 → 结果回填 → 正常结束
- 未知工具 / 参数错误 → ERROR 文本回填（模型可自纠）
- 轮次上限 / 无进展 → 策略停止
- Token 预算 → 熔断
- 软阈值 → 回合边界压缩
"""
```

`MockLLMClient` 按预置响应序列返回、记录每次请求的消息快照——测试可以断言"第二轮请求里有没有 ERROR 消息""压缩发生在哪一轮"。**这是自研内核的直接红利**：循环的依赖全是构造参数，替换任何一个不需要打桩框架。压缩时机的测试甚至精确到算术级（用 3000 字符 system 消息 + 100 字符工具结果 + `context_window=1500` 构造出"第 2 轮末恰好落入 SOFT"的确定性场景）。

**其三：真实事故的回归档案。** 三个测试文件本身就是"事故卷宗"——文件头注释保留了故障现场：

- `test_noise_control.py`："用 CodeSage 审查自己的 tests/ 目录时，发现 208 条候选里绝大多数是噪音……评分被扣到 0 分"（第 03 篇 3.5 的事故）；
- `test_models.py`："demo_target 演示中发现 Bandit 的英文发现（B307）把自研规则的中文发现（CG011，含具体修复建议）挤掉了——本文件锁定修复后的去重行为"（第 08 篇 8.2 提到的第二起事故）；
- `test_severity_mapping.py`："真实使用中 SQL 注入（Bandit 标 MEDIUM）与'缺 docstring'同为 P2 呈现——本文件锁定'高危规则按业务风险上调'的行为"（11.4 节展开）。

**事故 → 修复 → 用测试锁死**——这是项目里重复出现的改进模式；而"把事故背景写进测试注释"让每一条回归测试都有"为什么存在"的记忆。

## 11.3 容错哲学：降级清单

把散在各处的容错设计收集起来，是一条统一哲学：**辅助设施的任何失败，都不能把主流程带下水。**

| 故障 | 处理方式 | 位置 |
|---|---|---|
| 未配置 API Key | 降级确定性分析（不报错） | review 命令 / pipeline / eval |
| LLM 调用失败 | `LLMError` → `error` 状态，已收集的发现仍进报告 | 循环 |
| 工具执行异常 | 转 `ERROR: …` 文本回填，模型自纠 | 注册表 |
| 压缩器失败（异常/空返回） | 保持原状（"信息优先于成本"） | WorkingMemory |
| 未注入压缩器 | 压缩是空操作，循环照转 | 循环 `_compress` |
| 事件钩子抛异常 | 吞掉（观测不反噬主流程） | `_emit` |
| 错题本读取失败 | 空经验块继续 | pipeline |
| 外部分析器未安装 | 过滤跳过，其余照跑 | pipeline / `is_available` |
| 源码读取失败（OSError） | 跳过该文件 | pipeline 备料段 / scanner |
| 单条 AST 规则抛异常 | 跳过该规则，其余继续 | RuleEngine |
| 语法错误 | 报 CG000（MAJOR），不中断 | RuleEngine |
| 非 git 仓库 + `--changed` | 回退全量 + 明确提示（**不静默**） | pipeline |
| Store 打开/落盘失败 | 返回 None / 静默吞掉，审查继续 | `_open_store` / 落盘段 |
| 导出失败（OSError） | 友好提示 + 退出码 2（附正确用法提示） | review 命令 |

两个例子对照着看"降级"与"报错"的分界：

```python
    # 落盘失败不致命（只读目录 / 权限问题不应中断审查）
    if store is not None:
        try:
            review_id = store.save_review(report, project=str(workspace))
            ...
        except Exception:  # noqa: BLE001
            pass
```

落盘（辅助设施）→ **静默降级**。而"`--changed` 但检测不到变更"（用户意图的核心承诺）→ **明确报错**。判断标准不是"错误大小"，而是：**这个失败会不会让用户拿到的结果与他表达的意图不符？** 会 → 报清楚；不会 → 降级保平安。

## 11.4 反馈驱动的修复集：一份完整台账

10 月 12 日这轮里，项目集中修复了一批**真实使用中发现的问题**。这批修复是"这个工具被反复使用过"的最好证明——汇总如下：

| # | 问题（真实反馈） | 修复 | 测试锚点 |
|---|---|---|---|
| 1 | 存储写在"被审查目录/.codesage/"：**污染第三方项目**，且记录散落导致 history 看不到 | 迁移为用户级全局存储 `~/.codesage/store.db`，加 `project` 列隔离 | `test_store.py` |
| 2 | `history -p test.py` 报"暂无记录"，但记录其实在库里 | `_normalize_project`：文件路径归一到父目录，读写两端语义对齐 | `test_cli_helpers.py` |
| 3 | **SQL 注入与"缺 docstring"同为 P2**（不可接受） | Bandit 高危规则表 `_ELEVATED_RULES` 按业务风险上调（只升不降，上限 MAJOR） | `test_severity_mapping.py` |
| 4 | 模型提交的多行文本被双重转义，报告里显示一串 `\n` | `_normalize_escaped_newlines`（保守三条件，防误伤代码字面量） | `test_tools.py` |
| 5 | `-o D:\dir`（已存在目录）被当文件写入 → `PermissionError` | `_resolve_output_path`：目录感知，自动按 `<目标名>.codesage.md` 落名 | `test_cli_helpers.py` |
| 6 | `--changed` 在无变更时静默全量——**浪费 Token** | 三态语义：非 git 回退+提示 / 无变更明确报错 / 有变更过滤 | `test_changed_mode.py` |
| 7 | LLM 在前 3 轮"调查期"（读码/跑分析/查知识库）被无进展检测**过早掐断** | `ever_found` 分档：有提交耐心 2 轮、零提交宽限 4 轮 | `test_agent_loop.py` |
| 8 | 报告渲染把 `[B608]` 这类方括号当 Rich 标记吞掉 | 全链路 `escape()` + 多行建议逐行渲染 | （渲染层） |
| 9 | 守则 1 只说"属实则提交、误报则忽略"，模型执行不一致 | 改写：讲清两条通道的**后果**（提交则展示你的分析；不提交只剩通用提示） | 提示词演进 |
| 10 | 严重级有"critical"和"P0"两套指代，用户要自行翻译 | CLI 收 `P0-P3` 别名（`--min-severity P1` 可用） | （CLI 解析） |

**这批修复的共同特征**：几乎全部来自"用起来之后才暴露的问题"——不是设计时的疏漏，而是"设计对了、但产品体验还差一层"。三类最典型：

- **体验类**（#2、#5、#10）：用户直觉合理、工具行为较真——修复方向是"工具向用户习惯靠"；
- **语义类**（#3、#6、#7）：工具做得"没错"但"不对"——SQL 注入被标 MEDIUM 是 Bandit 的规则，但审查工具的呈现必须按业务风险；
- **修复类**（#4、#8）：触发条件的边界处理——双重转义、方括号吞噬这类"只在真实模型/真实终端上才出现"的问题。

每一行的"测试锚点"列就是防回归的保险——**修过的 bug 不允许复活**。

## 11.5 小结

- **性能**：92.7s → 2.1s（44 倍）；三个修复全在进程/I/O 模型层；方法论 = 基线（Harness 记录）→ cProfile 剖析 → 数据验证；起点是自举审查。
- **测试**：14 文件 / 119 用例 / 4.4 秒；正反例成对（规则）、Mock 驱动（循环）、事故回归（噪声/去重/严重级）三类最典型；事故背景写进测试注释。
- **容错**：十四条降级清单，一条哲学——辅助失败不带崩主流程；"降级 vs 报错"的分界是"结果是否背离用户意图"。
- **反馈台账**：十项真实使用驱动的修复，全部有测试锚点——这是"这个工具被真实使用过"的证据链。
