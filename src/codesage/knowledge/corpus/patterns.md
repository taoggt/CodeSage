## 何时建议设计模式（以及何时闭嘴）

### 明确的触发信号（出现以下信号才建议）

| 信号 | 建议模式 | 前提 |
|---|---|---|
| 长 if-elif 链按"类型/别名"分派不同行为 | 字典分派表 / 策略模式 | 分支 ≥ 5 且会持续增长 |
| 多个类共享复杂的构造流程（步骤固定、参数组合多） | 工厂 / 建造者 | 构造逻辑重复 ≥ 3 处 |
| 对象行为随状态字段大量切换（状态 + 转换规则散落） | 状态模式 | 状态 ≥ 3 个且有转换矩阵 |
| 跨切面逻辑（日志/计时/重试）散落在多个函数 | 装饰器 / 中间件 | 重复 ≥ 3 处 |

### 过度设计警戒线（禁止建议的情况）

- 单文件小工具（< 200 行）：**任何模式都是过度设计**；
- 只有 2-3 个分支的 if-elif：直接可读性更好，不要建议策略模式；
- 一次性脚本：不要建议抽象基类、依赖注入容器；
- 分支有明确注释且稳定：`if/elif` 是最诚实的代码。

### 推荐的轻量替代（优先于完整模式）

```python
# 完整策略模式（类 + 注册表）适合大型系统
# 轻量替代：函数 + 字典分派（Python 中 90% 场景够用）
HANDLERS = {
    "create": handle_create,
    "update": handle_update,
    "delete": handle_delete,
}
handler = HANDLERS.get(action)
if handler is None:
    raise ValueError(f"未知操作：{action}")
```

> 审查提示：架构级建议的措辞是"当 X 增长时，可考虑 Y"，
> 而不是"你应该用 Y 模式"。给出触发条件，让读者自己判断。
